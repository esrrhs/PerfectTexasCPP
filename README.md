# texas_cfr

德州扑克不完全信息博弈求解器，C++17 实现，无第三方依赖。

核心是 **CFR（Counterfactual Regret Minimization，反事实遗憾最小化）** 家族算法。这是
Libratus、Pluribus、DeepStack 击败人类职业选手时用的方法，而**不是** PPO / DQN 这类
标准强化学习。

## 为什么不用普通强化学习

德州扑克是**不完全信息博弈**：

| | 完全信息（围棋/象棋） | 不完全信息（德州扑克） |
|---|---|---|
| 决策点 | 局面唯一确定 | 信息集内无法分辨（对手底牌有多种可能） |
| 数学框架 | MDP | 扩展式博弈 + 信念分布 |
| 最优解 | 确定性策略（选价值最大的动作） | **混合策略**，必须按概率随机出招 |
| 求解目标 | 最大化收益 | 逼近**纳什均衡**（任何固定打法都会被剥削） |

所以这里求的不是"最优动作"，而是"让对手无法利用的策略分布"。

## 算法

CFR 每一轮迭代做四件事：

1. 用当前策略遍历博弈树，算出每个信息集里每个动作的反事实价值 `v(I,a)`
2. 累积遗憾 `R(I,a) += v(I,a) − v(I,σ)`
3. 后悔匹配更新策略：`σ(I,a) ∝ max(R(I,a), 0)`，越后悔的动作做得越多
4. 按到达概率加权累积**平均策略** `σ̄`

输出的是 `σ̄`，不是最后一轮的 `σ`。理论保证平均策略的可利用度以 `O(1/√T)` 收敛到 0。

本仓库实现了三个变体：

- **vanilla CFR**：标准形式
- **CFR+**：遗憾裁剪到非负 + 交替更新 + 线性加权平均，实测快 1.4 倍以上
- **DCFR**（无限注德州的默认）：在 CFR+ 基础上再按迭代轮数给正/负遗憾和平均策略打折

DCFR 的折扣来自 Brown & Sandholm (2019)：正遗憾打 `t^1.5/(t^1.5+1)`、负遗憾打
`t^0.5/(t^0.5+1)`、平均策略打 `(t/(t+1))^2`。直觉是"越早的迭代越不可信"，负遗憾打折
比正遗憾快等于允许策略较快放弃坏动作。实测同轮数下遗憾上界只有 CFR+ 的
0.51（4万轮）→ 0.42（10万轮）→ 0.37（20万轮），比值随轮数单调下降。

几个实现要点：

- **反事实加权**：累积遗憾时只乘对手的到达概率，不乘自己的——这正是"反事实"的含义
- **整数信息集键**：避免每次递归都构造 `std::string`，Leduc 上快一个数量级
- **O(n) 牌力评估**：13 位顺子表 + 花色/点数计数，比"21 组合 × 5 张评估"快 19.5 倍
- **模板化的游戏接口**：求解器与具体游戏零耦合，新增游戏只需提供静态接口
- **强度可测量**：策略可存盘成冻结基准，`match` 子命令拿两份策略对打并给出置信区间。
  零和对称游戏里自对局恒为 0、打随机对手又太软，只有固定基准对打才有分辨力

```bash

./build/texas_cli solve kuhn --iters 20000

# 训练 Leduc，写出 CSV 方便画收敛曲线
./build/texas_cli solve leduc --iters 10000 --report 1000 --csv leduc.csv
```

## 正确性验证

自测不靠"看起来能跑"，而是和**解析解**逐项对照：

**Kuhn Poker**（理论值 `-1/18 = -0.055556`）

```
value = -0.055646   误差 9e-5
exploitability = 0.001080   共 12 个信息集
```

均衡策略结构也完全对上（`card: 0=J 1=Q 2=K`，`p`=过牌/弃牌，`b`=下注/跟注）：

| 信息集 | 实测 | 理论 |
|---|---|---|
| P0 拿 J 主动下注 α | 0.235 | α ∈ [0, 1/3] |
| P0 拿 K 主动下注 | 0.696 | 3α = 0.705 |
| P0 拿 Q 主动下注 | 0.003 | 0（永不） |
| P0 拿 Q 面对下注跟注 | 0.571 | α + 1/3 = 0.570 |
| P1 过牌后拿 J 诈唬 | 0.338 | 1/3 |
| P1 面对下注拿 Q 跟注 | 0.339 | 1/3 |
| P1 拿 J 面对下注 | 0.000 | 必弃 |
| P1 拿 K 面对下注 | 1.000 | 必跟 |

**Leduc Hold'em**（文献标准值 `-0.0856`）

```
15000 轮  : value = -0.085152   exploitability = 0.0179
200000 轮 : value = -0.085446   exploitability = 0.0052
共 288 个信息集（精确值）
```

信息集按 rank 合并：两张 J 在博弈上完全等价（对手看不到花色、发牌分布相同），
所以 `P0 拿 J` 只算一个信息集。这样策略表更紧凑、打印也不重复；代价是收敛略慢于
按具体牌 id 存储的 936 个信息集版本。

**可利用度基准**：均匀随机策略的 exploitability 是 0.4583，训练 20000 轮后降到 0.0011，
下降 424 倍。

**胜率对照**（40000 次采样 vs 随机手牌）：AA 85.72%（理论 85.2%）、KK 82.57%（82.4%）、
72o 34.58%（34.6%）。

## Leduc 规则

- 6 张牌：J,J,Q,Q,K,K，两人各发 1 张私有牌，各放 1 注 ante
- 两轮下注。第一轮下注额 2，**第二轮翻倍为 4**（Southey et al. 2005 的标准定义）
- 每轮最多 2 次加注（首次下注记作第 1 次），第二轮开始前翻 1 张公共牌
- 成对（手牌 rank == 公共牌 rank）胜过非成对，都非成对时比 rank

## 无限注德州（完整规则）

`holdem.hpp` 是完整的无限注德州规则引擎：

- 52 张牌、四条街（翻牌前 / 翻牌 / 转牌 / 河牌）
- 无限注下注，每街最多 3 次加注（够打到 4-bet）
- 加注尺寸分街处理：翻牌前按当前最大投入的 2.5x / 4x（开池、3-bet、4-bet 自然成阶梯），
  翻牌后按底池比例的 半池 / 一池；always 额外提供 all-in
- all-in 后一次发完剩余公共牌、**边池分层结算**、摊牌比牌，支持 2～6 人
- 盲注、行动顺序、无人下注时不可弃牌等边界都有单测覆盖

### 为什么必须抽象

HUNL 原始决策点约 10^160，这里做两层压缩。

#### 1. 牌力抽象（`strength.hpp`）

分三段，逐段控制精度损失。

**翻牌前：169 类手牌全分辨率使用，不分桶。** 这一条非常关键：翻牌前本来只有 169 个
可区分信息（13 个对子 + 78 个同花 + 78 个非同花），再压成 10 个桶会把 AA 和 KK、
AKs 和 AKo 合并成**同一个信息集**——策略上就是完全相同的动作分布。早先版本就是这样，
输出里 AA 和 KK 的策略逐位相同。类内所有具体组合对随机对手的胜率严格相等（花色置换
对称），所以每类取一个代表组合、用 3 万次蒙特卡洛估胜率就够。

**翻牌后百分位：精确秩表，不是分位点近似。** 5 张牌用 C(52,5) 精确枚举，6/7 张用
150 万 / 200 万次采样。关键观察是"7 张牌里最佳五张"的**不同取值只有不到 7500 种**
（5 张恰好 7462 种），所以"分数 → 严格小于它的组合数"可以完整存下来，表只有几十 KB，
查询是精确百分位，二分定位。

早先用 4096 个分位点近似，量化步长 1/4096 ≈ 0.0244%，而"四条"整个牌型只占 0.024%
的牌——**一个牌型比一个量化步长还窄**，结果四条和同花顺被压成同一个百分位。

**翻牌后潜力修正。** 只看"当前最佳五张的排名"会严重低估听牌：花听在当前牌力里只是
高牌（百分位 0.46），实际价值接近中等成牌。所以按听牌出路（outs）用超几何分布算命中
概率，对百分位做期望修正：

```
eff = (1 - p_hit) * 当前百分位 + p_hit * 命中后的百分位
```

`p_hit` 用精确的 `outs / 未见牌数`（两张牌到来时用 `1 - C(a,2)/C(b,2)`），outs 按具体
牌去重后数（花听 9 个，两头顺 8 个，卡顺 4 个）。命中后的百分位取该牌型在本张数下的
区间中点——边界不是写死的常数，而是从真实分数分布里取的。

#### 2. 分桶：按牌型分配，不是等质量分位

这一步是**不能用等质量分桶**的。5 张牌里"两对及以上"只占 8.2%，20 个等质量桶下，
两对、三条、顺子、同花、葫芦、四条会**全部挤进最后一个桶**——模型分不清"超对"和
"暗三条"，翻牌后策略直接废掉，而且这不是加迭代数能救的。同理，任何单调变换都救不了，
因为问题在于给尾部分配了多少质量，不是映射形状。

所以九个牌型各自拿到一段百分位区间，区间内部再等分成若干子桶，桶位按牌型权重用最大
余数法分配（总数精确等于 `--buckets`）。牌型边界同样由真实分布得出，5/6/7 张各不相同。

效果（20 桶，九个牌型各构造一手牌验证）：

```
高牌=1 一对=6 两对=9 三条=10 顺子=13 同花=15 葫芦=16 四条=18 同花顺=19
```

严格单调、互不重叠。等质量分桶下这里是 `… 两对=19 三条=19 顺子=19 同花=19 葫芦=19`。

因为作用在潜力修正后的 `eff` 上，听牌被抬起来之后可以跨过牌型边界往上走，不会被人为
压在底层。

#### 3. 动作抽象

每个决策点最多 6 个动作（弃牌 / 跟注 / 至多 3 档加注尺寸 / all-in），每街最多 3 次加注。
`kMaxActions = 6` 就是被这个结构定死的：弃牌和跟注各占 1 个，all-in 占 1 个，剩 3 档。

早先版本翻牌前用的是底池比例：底池只有 3，算出来的加注是"加到 4"和"加到 5"，而下一个
选项直接就是全下 200。**中间 5 到 200 之间有 195 个筹码的空洞**，模型想造大底池只能全下，
策略退化成"要么跛入要么推"。翻牌前改用当前最大投入的倍数就解决了。

##### 把尺寸做成参数，才能测"哪种尺寸更好"

早先尺寸是写死在 `actions()` 里的，于是这件事根本测不了——一套二进制只能用一套动作集。
现在换成 `ActionSpace`：

```cpp
struct ActionSpace {
    int preflopMul1000[3] = {2500, 4000, 2500};   // 翻牌前加注到 maxRC × 2.5 / 4
    int preflopCount = 2;
    int postflopFrac1000[3] = {500, 1000, 500};   // 翻牌后加注到 maxRC + 底池 × 1/2 / 1
    int postflopCount = 2;
    bool includeAllIn = true;
};
```

默认值**与早期的写死版本逐位等价**（`x + floor(1.5x) == floor(2.5x)`，奇数 `x` 也成立），
所以所有已训模型和基准快照不受影响；测试里专门有一个块对比两条路径的金额。

CLI 用 `--sizes` 选预设：`default` / `one` / `three` / `nojam` / `small` / `big`。
名字表只有一份（`holdem.hpp` 里的 `actionPresets()`），名字→动作集与动作集→名字都读它。
打印那一行按**实际在用的动作集**反查名字，不回显 `--sizes` 的字符串：读盘时动作集以
文件为准，此时命令行那个名字已经不是实际在跑的东西了，会被显式提示覆盖。测试
`testActionSpaceNaming` 钉住这条往返——名字和动作集各漂各的时，输出会变成
"动作集 three：翻牌前 2 档"这种自相矛盾却不报错的形状。`--no-sized-history` 是复现
旧缺陷用的开关，不是优化项。

##### 对照实验：尺寸到底该怎么选

每个候选按自己的动作集训练、按自己的动作集出招（受限抽象互相打）、相对默认打 6 万副牌
配对、座位对称化。两个预算档各跑一遍，结论一致：

| 动作集 | 信息集 | 轮/s | 相对默认 @50万 | 相对默认 @100万 |
|---|---|---|---|---|
| 默认 2.5x/4x + 半池/一池 | 620626 | 56081 | 0（基准） | 0（基准） |
| 只 1 档（2.5x + 一池） | 61789 | 153365 | **−1.19 ± 0.41** | **−1.52 ± 0.37** |
| 默认尺寸去掉 all-in | 552542 | 44482 | **−0.95 ± 0.40** | **−1.01 ± 0.35** |
| 小尺寸 2x/3x + 1/3,3/4 池 | 2242454 | 30800 | +0.31 ± 0.46 | +0.29 ± 0.43 |
| 大尺寸 3x/5x + 一池,两池 | 113162 | 116052 | −0.01 ± 0.46 | −0.04 ± 0.43 |

三条结论：

1. **只留 1 档明显更弱**（−1.2 ~ −1.5）。这量化了"多一档尺寸值多少"。
2. **去掉 all-in 明显更弱**（−0.95 ~ −1.01）。这一条**否证了上一版的猜想**——上一版说
   "独立的全下动作制造了尺寸空洞、是收益泄漏点"，实测正好相反：把这条路封死更亏。
   先前"这个动作偏差不是主要泄漏点"的推理方向是对的，但原因搞错了。
3. **具体挑哪两档尺寸，测不出差异。** 换小、换大都在噪声里。有意思的是"大尺寸"
   （3x/5x + 一池/两池）只用了 **5.5 倍少的信息集**、吞吐高 **2.1 倍**，强度却打平——
   因为尺寸大，钱更快打光，下注树自然更浅。

##### 3 档尺寸：不是更好，是更贵

这里踩了个坑，也顺便暴露了一个潜伏的求解器 bug（见"死循环"一节）。3 档（每街 3 档尺寸
+ all-in）在等预算下**并不更好**：

| 预算 | 信息集 | 遗憾上界 | 轮/s | 相对默认 |
|---|---|---|---|---|
| 10 万轮 | 2731673 | 3632.6 | 22045 | +0.52 ± 0.59（不显著） |

信息集是默认的 4.4 倍（10 万轮时），训练慢 2.6 倍；50 万轮时表涨到几百万条、单轮慢几十倍，
跑到 26 分钟都没结束。**在"每街最多 3 次加注 + 连续尺寸"这个结构下，加第三档尺寸买不到
可测的收益。**

### 信息集划分：应对方必须看得见下注额

这是这一轮最重要的发现，而且它不是调参问题，是一个**结构性缺陷**。

`next()` 里所有加注都只往历史里推一个 `'r'`：

```cpp
++t.raises;
t.pushHist('r');          // 加注到 5、8、200 都只有这一个字符
```

于是"加注到 5"、"加注到 8"和"加注到 200"产生**完全相同的历史哈希**。应对方拿到的是
同一个信息集，它根本分不清自己面对的是小额加注还是 100BB 全下，只能对这两种截然不同
的局面强行用同一套动作分布。

这不是边角情况。枚举可达下注树（深度 16）可以看到丢失的规模：

| 度量 | 实测 |
|---|---|
| 不同的动作字符序列 | 4442 个 |
| 这些序列背后真实的筹码局面 | 49501 个 |
| 一个序列对应多个局面的 | **3796 / 4442（85.5%）** |
| 平均每个序列藏着几个局面 | **11.14 个** |
| 最坏的一个序列 | 藏了 **36** 个不同局面 |

**修法**是每次加注时额外把"加注后的本街投入额"混进另一个历史哈希：

```cpp
void mixRaiseSize(int roundContribAfter) {
    histSizedHash ^= static_cast<std::uint64_t>(static_cast<std::uint32_t>(roundContribAfter));
    histSizedHash *= 1099511628211ULL;
    histSizedHash ^= histSizedHash >> 29;
}
```

混入的是投入额而不是"这是第几个加注按钮"。两者对信息集的切分等价（尺寸由状态唯一决定，
投入额与按钮号互相可推），选投入额是因为它不依赖动作集的定义——将来换掉下注尺寸表，
这里不用跟着改。

`State` 同时维护 `histHash`（只含字符）和 `histSizedHash`（含尺寸），抽象用
`HoldemAbstraction::sizedHistory` 挑一个。多一个 `uint64_t` 的开销是每次动作一次乘加：
一轮约 24 个动作，按总时间 15 µs/轮算占千分之几，可以忽略。它换来两件事：**两种划分能在
同一进程里训练并直接对打**，以及这个缺陷从此被测试钉死，不靠人肉记忆。

#### 到底有多大影响

带着 200 万副牌的配对对打（同底牌同公共牌、座位对称化）：

| 对比 | 每手净筹码 |
|---|---|
| 看得见尺寸 打 看不见尺寸 | **+2.3053 ± 0.1802** |
| 看不见尺寸 打 看得见尺寸（反对称检查） | −2.2210 ± 0.1802 |
| 两者相加（应为 0） | +0.0843 ± 0.2548 |

约 **13σ**。注意这里有个反差：看得见尺寸的模型在自己那个游戏里**收敛得差得多**
（信息集 3.8 万 → 59 万，15.4 倍；遗憾上界 36.6 → 307.4；单轮慢 2.46 倍），却仍然把
收敛得更好的破抽象打得落花流水。**抽象的正确性比收敛程度重要得多。**

行为上也立刻能看出来。同一手 AA 在 K83 面上先过牌、面对小盲下注时的平均策略：

|---|---|---|---|
| 半池（2） | 0.14 | 0.79 | 0.07 |
| 一池（4） | 0.45 | 0.47 | 0.08 |
| 全下（200） | 0.69 | 0.31 | — |

修复前三档共用同一个信息集，只能吐出同一个数。

上一版 README 猜"尺寸盲可以解释过度全下"。**实测否证了这个猜测**：修复后 22 仍然在
翻牌前全下 0.61（AA 是 0.00）。全下偏差另有来源，仍然待查。

### 求解器

`mccfr.hpp` 用 external sampling MCCFR：轮到 traverser 展开全部动作，对手和机会节点各
采样一个。全树遍历不可行——光翻牌就有 C(48,3)=17296 种组合。

信息集 =（街，牌力桶，下注历史），这才让"具体手牌"塌缩成有限状态。下注历史里**必须包含
每次加注的金额**，否则应对方看不见自己面对的是什么尺寸（见上一节）。

两处关键实现：

- **整副公共牌在根节点一次抽定。** 这与逐街条件抽牌的联合分布完全相同，但整棵树共用
  一副公共牌，"牌力桶"就能按 (玩家, 街) 在本轮内缓存——实测每轮桶计算从 74 次降到 6 次。
  缓存用 `bucketStamp_[p][bc] == iter_` 做版本标记，跨轮自动失效。
- **摊牌牌力也按 (玩家, 公共牌张数) 缓存。** 同理，一轮内底牌和公共牌固定，同一个摊牌
  的牌力会被反复重算（当时实测每轮约 38 次 `evaluate7`）。`ScoreCache` 把它压到最多 6 次，
  吞吐涨 13%（137k → 153k 轮/s，这是修正信息划分之前的数），行为逐位不变。
- **下注历史用增量哈希。** `State` 里存两个 64 位哈希 + 定长字符缓冲，`next()` 里 O(1) 更新。
  早先用 `std::string`，每个节点拷一次堆分配、每个信息集键把整条历史重新哈希一遍。
  两个哈希只差"有没有混入加注额"这一维，为的是能对打比较两种信息划分。

遗憾累计默认用 DCFR（`--variant cfrplus` 可切回），折扣因子每轮算一次就够——一轮遍历
里一个信息集最多被更新一次。**平均策略的加权方式两个变体必须分开**：CFR+ 靠线性权重
`w = t`，而 DCFR 的 `(t/(t+1))²` 折扣本身就是加权（等价于权重 ∝ k²）。两者叠加会让
权重变成 k³、平均窗口压到只剩最后 16%，实测后果是训练越久策略越弱。

信息集表是平坦开放寻址而非 `std::unordered_map`：遍历里每个决策节点都要查一次，
`unordered_map` 的指针追逐很贵。扩容只在两轮之间做（`prepare`），因为 `traverse` 会跨
递归持有 `InfoSetData&`，一旦中途 rehash 引用就悬空了。

### 性能剖析（实测，不是猜）

一轮遍历平均走 **163.96 个节点**：62.14 个终局、19.38 个机会节点、24.47 个 traverser
决策点、57.97 个对手决策点，桶重算 6.25 次。（修尺寸可见性之前是 102.4 个节点——玩家现在
更爱加注，树更深，多了 60% 的节点。）

每节点成本有一个反直觉的变化：同一份代码、同一个 20 桶配置，**看不见尺寸时 56.3 ns/节点，
看得见尺寸时 96.6 ns/节点（1.72 倍）**。节点数只多 60%，单节点却慢了 72%，说明有额外开销。

猜想是信息集表大到装不进 cache。树的大小由下注结构决定，桶数只改表的大小——于是固定
下注结构、只扫桶数：

| 桶数 | 信息集 | 表大小 | 每轮节点数 | 每节点 |
|---|---|---|---|---|
| 4 / 8 | 254472 | 25.2 MB | 164.0 | 80.3 ns |
| 12 | 351163 | 34.8 MB | 167.3 | 93.1 ns |
| 20 | 591931 | 58.7 MB | 161.8 | 97.6 ns |
| 40 | 1119875 | 111 MB | 155.8 | 104.3 ns |

节点数基本恒定（156~167），每节点却单调变慢——**表的大小就是原因**。条目本身是
`sizeof(InfoSetData) = 104` 字节（`2 × kMaxActions × double + int`，`kMaxActions = 6`），
62 万条就是 61.6 MB，远超 L2。这是把加注额纳入信息集的代价之一，也是下一个明确的优化点：
把遗憾和平均策略改存 `float` 能把条目压到约 52 字节，表直接减半。

用 `sample` 解析叶节点自耗时，`traverse` 自己占大头，其余单项都不超过 2%——
**成本摊在 160 多次递归调用上，没有单点大头**。这一点花了三次实验才确认：

| 猜想 | 结果 | 结论 |
|---|---|---|
| `handScore` 是瓶颈（消融：恒返回 0） | 反而慢 30% | **消融被策略漂移污染**：平局变多→策略变均匀→对手少弃牌→树更深。算法会自适应，不能用消融 |
| `State` 太大（缩到 177 字节） | 无变化 | `State` 拷贝实测只有 **0.9 ns**，编译器直接消掉了 |
| 信息集表随机访问 cache miss | 14.2 ns/次 | 表从 4000 增到 39277 项只多 6 ns；但超过 25 MB 之后代价就明显了（见上表） |

顺带否掉两个"听起来很值钱"的优化：缩小 `hist` 缓冲（64 字节，其实 `histString()` 是死代码）
和换更小的信息集结构，都不影响吞吐。

### 修掉一个会让求解器死循环的潜伏 bug

把动作集做成参数之后，3 档尺寸的变体跑 100 轮就不动了。`sample` 采样显示栈里全是
`traverse`，看起来像无限递归——但内存稳定在 11.6 MB，不像栈爆。真正的原因更难看：
**`InfoSetTable::get()` 的线性探测在表被填满后会永远找不到空槽**，而 `get()` 是内联的，
所以剖析工具把这段死循环算到了调用者头上，完全指错了方向。

这是个潜伏已久的缺陷。原来的设计有一条**没人强制、只靠约定**的不变量：

```cpp
// iterate() 里写死的预留量
isets_.prepare(256);   // 注释说"一轮最多新增 152 个信息集"
```

默认动作集下一轮确实只新增 152 个左右，所以从没触发过。3 档动作集一轮新增 **330** 个——
超过预留量，表被填满，`get()` 死循环。

修法三处：

1. **`get()` 插入前自己保证余量**：负载将超过 0.7 就先扩容。不再依赖调用方"预留够多"
   这条约定，对任意动作集都成立。
2. **`traverse` 在递归之后按 key 重新取一次信息集。** 扩容会让它递归前拿到的
   `InfoSetData&` 失效；原来"整轮内引用稳定"是成立的，现在扩容可能发生在轮内，所以必须
   重取。这一条是 1 的前提——没有它，修好死循环会换成悬空引用。
3. **预留量按实测自适应**：记下上一轮实际新增了多少，下一轮预留它的两倍。这只是性能优化，
   有了 1 之后即使预留不足也只是多一次扩容。

代价是每个 traverser 节点多一次查表：10 万轮从 1.33 秒变成 1.35 秒，约 1.5%。
默认动作集的输出**逐位不变**（468557 信息集 / 遗憾上界 805.81），说明改动没有影响数值。

教训：那条"扩容只在两轮之间做，所以引用稳定"的不变量是**承重**的，但它写在注释里、
没有任何机制保证。现在它由代码结构保证，而不是由记性保证。

### 已验证

牌力评估（确定性）：

- `evaluateBest` 快路径与 21 组合暴力实现**逐位等价**：C(52,5) 全量 2598960 组、
  C(52,6) 全量 20358520 组、随机 500 万组 7 张，**0 处不一致**
- 速度 734ns → 37ns（19.5 倍）
- 秩表规模自洽：5 张不同牌力取值恰好 7462 种，与扑克理论公认值一致

牌力抽象（确定性）：

- 翻牌前 169 类各自独立：AA/KK、AKs/AKo、AA/72o 类号互不相同，花色置换不变
- 胜率排序 AA 0.856 > KK 0.822 > QQ 0.799 > AKs 0.676 > AKo 0.659 > 72o 0.340
- 同一块 K72 面上 `AhTh` 与 `AdTd` 的**当前牌力百分位严格相等**（都是 A 高牌，都是 0.463），
  但前者有 9 个花听出路，修正后 0.463 → 0.650，必须显著更高
- 两头顺听牌 8 个出路、卡顺 4 个；河牌没有后续牌，修正退化成百分位本身
- 九个牌型在 20 桶和 50 桶下都严格单调、互不重叠

规则引擎：

- 盲注、行动顺序、翻牌发牌、无人下注不可弃牌
- 摊牌比牌、弃牌结算、两人零和
- 三人边池：主池 150 由三人争、边池 100 由 P1/P2 争，两种赢家情形下净收益和均为 0
- all-in 后一次发完 5 张公共牌并摊牌

摊牌牌力缓存（确定性）：

- 6 张牌快路径（`evaluate6`）与"枚举 6 选 5 的所有子集取最大"对照 2 万组，0 处不一致
- 2 万局引擎自走的**合法对局**（含 12235 局摊牌）上，带缓存与不带缓存的结算逐位相同，
  零和违例 0 处
- 注意这条测试不能用"手搓的随机状态"：手搓可能让弃牌者投入高于存活者，那种局面在真实
  对局里不可达、结算本身就不守恒，拿它测缓存只会测出噪声。同理每局必须用唯一 stamp —
  缓存的约定就是"同一 stamp 内底牌和公共牌固定"，违反约定得到错误结果不算 bug

求解器（确定性）：

- 存盘 / 读盘往返后，两手牌的平均策略**逐位相同**，信息集数与轮数也一致
- 读不存在的文件返回失败而不是崩溃
- 同一策略在两个座位自对打，结果落在 0 的置信区间内（校验 `headToHead` 的座位对称性）
- 遗憾上界随轮数下降；同轮数下 DCFR 低于 CFR+。10 万轮实测比值 0.720，且随预算单调
  下降（20 万 0.638 / 50 万 0.554 / 100 万 0.503），6 个种子的比值落在 0.706~0.747。
  阈值取 0.80——**不要把它当"DCFR 只赢 20%"读**，同预算对打在 10万/20万/50万/100万 分别
  +1.96/+1.32/+1.08/+1.06 筹码每手（6.7~9.0σ）
- 信息集划分：同一节点下的三个加注动作（加注到 5 / 8 / 200）在"看得见尺寸"下给出三个
  互不相同的键，在"看不见尺寸"下塌成同一个键；无加注路径上两个历史哈希逐位相同；
  哈希格式被手工折算钉住，改了会让已存模型全部失效

策略（统计量，非确定性）：

- 50 万轮后：AA 加注 0.520 / 弃牌 0.002；72o 加注 0.016 / 弃牌 0.978
- 该断言用 8 个种子各跑 50 万轮实测过：AA 弃牌最高 0.0020、72o 弃牌最低 0.921、
  `raiseAA > raise72` 在 8/8 个种子上成立，最紧一次是 5.84 倍
- **但"AA 比 72o 激进多少倍"不稳定**：同样 8 个种子，比值分散在 5.84 到 1084 之间
  （后者分母已经接近 0）。所以测试只断言序关系和弃牌率，不断言倍数

### 怎么判断"确实更强"

零和对称游戏里**自对局恒为 0**，打均匀随机对手又太软抓不住差异，所以强度验证必须
有个固定基准。`save` / `load` + `match` 就是为此存在的：

```bash
# 1. 冻结一个基准，之后永不重训
./build/texas_cli holdem --iters 500000 --variant cfrplus --save base_cfrplus.bin

# 2. 候选策略（多个种子）逐个对打
for s in 1 777 12345 99991 31337; do
  ./build/texas_cli holdem --iters 500000 --seed $s --save cand.bin
  ./build/texas_cli match --a cand.bin --b base_cfrplus.bin --hands 600000
done
```

这个协议有两个坑，都踩过：

- **单个基准快照自带强度偏移。** CFR+ 用不同种子对打同一个 CFR+ 基准，结果不是 0 而是
  **+0.122 ± 0.062**（5 个种子全为正）——说明那个基准恰好比平均弱一点。所以不能拿
  "相对基准的绝对收益"当结论，要用**两个候选取差值**，基准偏移 β 在相减时抵消。
- **分辨率要算清楚。** 每手净收益的标准差约 149 筹码（全下就是 ±200 的摆动），
  想分辨 0.05 筹码/手需要 `(149/0.05)² ≈ 890 万手`。

DCFR 与 CFR+ 的对照（同 50 万轮、20 桶、5 个种子、每组 120 万手）：

| 候选 | 相对基准每手净收益 | 遗憾上界 |
|---|---|---|
| CFR+ | +0.122 ± 0.062 | 116.6 |
| DCFR | +0.413 ± 0.082 | 36.9 |
| **差值（DCFR − CFR+）** | **+0.291 ± 0.103（2.8σ）** | 约 1/3 |

单份快照对打（DCFR 20 万手 vs CFR+ 20 万手，两座位合计 80 万手）复现出更大的
**+0.7335 ± 0.1566**，那是含了快照自身波动的数值，所以区间比多种子均值更宽。

### 配对比较能省多少样本？取决于候选有多像

`match` 默认让两边独立发牌，单副牌收益的标准差在 40~50 筹码之间（一次全下就是 ±200 的
摆动）。如果**两边的牌完全一样**（同一底牌、同一公共牌），发牌噪声就在两者之间抵消。
用 `reveal` 把公共牌预先发定就能做到。

但"能省多少"这件事上一版说错了。同一个估计量（看得见尺寸 打 看不见尺寸 的每手净收益），
两种协议各估 10 万副牌 × 2 座位：

| 协议 | 均值 | 单副牌 σ | 标准误 |
|---|---|---|---|
| 独立发牌 | +1.9895 | 47.92 | 0.1515 |
| 同一副牌配对 | +2.0997 | 40.97 | 0.1295 |

**只省 1.37 倍样本，不是 16 倍。** 原因很清楚：配对只能抵消"同一副牌"这一部分噪声，
而这两个候选打法差别极大，剩下的动作采样噪声占主导。上一版那个 16 倍是在比较
10/14/20 桶这种**几乎一样**的候选时测的——那时候两者在同一副牌上的结果高度相关，
配对的效果才那么夸张。**所以"配对比各打一遍省 N 倍"不是一个固定数字，它随被比较的
两个策略的相似程度变化。**

精确枚举（对已发定的牌枚举整棵策略树求期望）能把 σ 压到 9.4，但单次约需 9600 个节点
（是采样的约 100 倍），按单位时间算方差反而是采样版的 3 倍。所以只在"要固定在某一副牌上
评估"时才值得用。

策略合理性上 DCFR 也一并压住了全下冲动（20 桶、看得见尺寸、各 50 万轮，同种子）：

| | CFR+ | DCFR |
|---|---|---|
| AA 平跟 | 0.59 | 0.48 |
| AA 加注（非全下） | 0.18 | 0.52 |
| AA 全下 | 0.22 | 0.00 |
| 72o 弃牌 | 0.86 | 0.98 |
| QJs 加注 / 全下 | 0.42 / 0.27 | 0.75 / 0.16 |
| **169 类平均全下频率** | 0.1175 | **0.0444** |

最后一行比单看几手牌更有代表性：DCFR 把翻牌前的平均全下频率压到 CFR+ 的 38%。

### 瓶颈到底在哪：算力还是抽象？

上一版 README 断言"50 万轮就到平台期，再训练没有可测收益，限制因素已经变成抽象本身"。
**这一轮的结论是：那个平台期大部分是尺寸盲造成的假象，结论要再改一次。**

用固定的"看不见尺寸 @50 万轮"当标尺（它的遗憾上界只有 36.6，已经把自己那个错的游戏
解干净了），让"看得见尺寸"在各预算下分别去打它，200 万副牌配对：

| 轮数 | 信息集 | 遗憾上界 | 相对标尺（筹码/手） |
|---|---|---|---|
| 12.5 万 | 490692 | 716.34 | +1.0402 ± 0.3787 |
| 25 万 | 548614 | 475.61 | +1.7831 ± 0.3534 |
| 50 万 | 591931 | 307.43 | +2.0584 ± 0.3285 |
| 100 万 | 620626 | 196.44 | **+2.5108 ± 0.3067** |
| 200 万 | 638208 | 124.19 | +2.3997 ± 0.2919 |

两点：

1. **只要 12.5 万轮的"正确抽象"，就已经打赢 50 万轮的破抽象**（+1.04 ± 0.38）。
2. 强度一直涨到 100 万轮才平：1M 与 2M 相差 −0.11 ± 0.22，在噪声里。CLI 默认因此从
   50 万改成 100 万。

注意强度饱和得**比遗憾上界早**：上界从 716 一路降到 124（还在降），但 1M→2M 的强度已经
测不出差别。也就是说"遗憾上界继续下降"并不等于"打得更强"，用它当强度代理要留神。

同样的协议重测桶数（配对同牌，20 万副牌，各 100 万轮，基准 = 20 桶）：

| 桶数 | 信息集 | 相对基准 | 判定 |
|---|---|---|---|
| 10 | 301383 | +0.1094 ± 0.1824 | 不显著 |
| 14 | 430411 | +0.1544 ± 0.1830 | 不显著 |
| 20 | 620626 | 0（基准） | — |
| 28 | 826353 | +0.1593 ± 0.1841 | 不显著 |
| 40 | 1198978 | −0.0366 ± 0.1835 | 不显著 |

**上一版"14 桶显著更弱、28/40 也不更好"的结论作废。** 修正信息划分之后，10 到 40 桶之间
测不出任何差异（全部 |Δ| ≤ 0.16，噪声 ±0.18），而且这些差异比尺寸可见性带来的 +2.31
小一个数量级以上。20 桶保留为默认值——理由不再是"它最强"，而是它在牌型分桶上不会把超对
和暗三条压进同一桶（10 桶会），且在噪声范围内与任何其他选择等价。

结论：**当前的瓶颈确实在抽象，但不是牌力抽象的粒度，而是动作抽象和整体表示能力。**
把桶数从 10 调到 40 换不到可测收益，说明继续在这一维上加细是白费力气。

### 修掉一个自己埋的加权 bug

DCFR 的 `(t/(t+1))²` 平均策略折扣**本身就是加权方式**（等价于权重 ∝ k²）。上一轮实现时
又额外乘了线性权重 `iter_`，权重变成 k³，平均窗口被压到只剩最后 16%。后果是训练越久
平均策略越弱——500 万副牌配对下，100 万 / 200 万轮相对 50 万轮是
**−0.225 ± 0.163 / −0.269 ± 0.165（显著更差）**。去掉重复的线性权重后变成
−0.091 / −0.064（不显著）。这个 bug 不是靠读代码发现的，是靠"训练更久应该更好"这个
反直觉现象追出来的。

### 还没做的

- **过度全下仍在，而且已经排除了一个猜测。** 100 万轮时 22 仍然在翻牌前全下 0.61
  （AA 是 0.00）；DCFR 把 169 类平均全下频率压到 0.0444，但个别手牌上的全下偏差还在。
  上一版猜"尺寸盲导致过度全下"，**修好尺寸可见性后这个现象没变**，所以猜测是错的，
  来源仍未查明。既然 200 万轮在对打里并不更强，说明这个动作偏差并不是主要的收益泄漏点
  ——两件事的张力还没有完全解释清楚。
- **主要矛盾在动作抽象和整体表示，不在牌力抽象。** 10 到 40 桶测不出任何差异（见上），
  所以继续在桶数上加细是白费力气。当前每街只有 3 个加注动作（2.5x/4x/全下，翻牌后
  半池/一池/全下），"独立的全下动作"在 100BB 深筹码下与相邻尺寸之间隔着一个巨大的空洞。
- **动作抽象还没法做对照实验。** `HoldemGame::actions()` 是静态的，一套二进制只能用一套
  动作集，所以"哪种加注尺寸更好"现在测不了。要做这件事得把动作集参数化，让引擎能同时
  支持多套抽象并互相打——这是下一步最值得做的重构。`sizedHistory` 这个开关是同类思路的
  第一个实例（只改信息划分、不改游戏），可以直接照它的样子做。
- **信息集条目可以减半。** `InfoSetData` 是 104 字节，62 万条就是 61.6 MB，远超 L2；
  实测每节点成本随表大小单调上升（25 MB → 80 ns，111 MB → 104 ns）。遗憾和平均策略改存
  `float` 能把条目压到约 52 字节、表直接减半，预期能拿回一部分吞吐——**但没测过**，
  精度损失对收敛的影响必须先用对打验证，不能只看吞吐。
- 要让策略真正可用，路线是：蓝图策略 + 实时子博弈求解（DeepStack / Libratus 路线），
  或者把 MCCFR 换成公有树 + 手牌向量化的向量化 CFR，用 GPU 跑。
- 分桶还可以再往前走一步：potential-aware 的二维特征（当前胜率 × 后续街胜率）加
  OSS / k-means 聚类，而不是现在的一维投影。
- **评估方法本身也迭代了两次、结论翻转了三次。** "新旧抽象对打打平"（分辨率 ±0.5）、
  "桶数 14 显著更弱"（分辨率 ±0.34）、"50 万轮到平台期"——这三条都是被更好的评估协议
  推翻的。**分辨率不足时，"打平"和"更差"这两个结论都不可信。** 连"配对能省 16 倍样本"
  也是错的：那是比较几乎相同的候选时的特例，候选差别大时只省 1.37 倍。
